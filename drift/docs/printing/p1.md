# P1: Foundation of the Drift Printing Language

This document explains how the current Drift language works at the foundation level, specifically for the `say` statement and printing pipeline.

## 1. Goal of the milestone

The purpose of this step is to build the smallest possible working interpreter for one command:

```drift
say "Hello World"
```

This version does not implement variables, conditionals, loops, functions, or files. It focuses only on the core execution flow:

- read source text
- tokenize input
- parse a single print statement
- execute the AST
- print output

This is the foundation of the language, and it follows the correct interpreter architecture:

Source Code
  ↓
Lexer
  ↓
Tokens
  ↓
Parser
  ↓
AST
  ↓
Interpreter
  ↓
Output

## 2. Language rule for printing

The language currently supports one statement:

```drift
say "Hello"
```

or

```drift
say "Hello World"
```

It also supports printing a literal string followed directly by a variable reference:

```drift
say "Hello "name
```

Rules:

- `say` is the keyword
- the text must be inside double quotes
- a variable name may follow immediately after a string literal without additional spaces
- one statement per line
- no semicolons
- spaces are ignored by the lexer where they are allowed, but they are not required between a closing string quote and a variable name
- escape sequences such as `\n` are translated into real newline characters when scanning a string literal

Example:

```drift
say "hello\nworld"
```

prints:

```text
hello
world
```

## 3. Token system

The token layer is the smallest meaningful unit of syntax in the language.

Token types currently supported:

- `TOKEN_SAY`
- `TOKEN_STRING`
- `TOKEN_NEWLINE`
- `TOKEN_EOF`
- `TOKEN_UNKNOWN`

Files involved:

- `include/drift/token.h`
- `token/token.c`

### What token.h does

This file declares the token model used by the interpreter:

- `TokenType` enum
- `Token` struct
- helper function declarations such as string duplication and token array cleanup

### What token.c does

This file provides the actual implementation of token utilities:

- `drift_duplicate_string()` copies a C string safely
- `token_free_array()` frees a token list and its string values

This keeps memory ownership clean and avoids leaking strings when the lexer or parser is done with them.

## 4. Lexer layer

The lexer reads raw source text and converts it into tokens.

Files involved:

- `include/drift/lexer.h`
- `lexer/lexer.c`

### What lexer.h does

It defines the `Lexer` structure:

- `source`: pointer to the source text
- `index`: current character position
- `length`: total source length

### What lexer.c does

This file handles tokenization for the language.

#### Responsibilities

- skip whitespace like spaces and tabs
- detect `say` keyword
- read double-quoted strings
- handle escaped newline sequences like `\n`
- emit `TOKEN_NEWLINE` when a line ends
- emit `TOKEN_EOF` at the end of input
- report syntax errors for malformed strings

#### Example

Input:

```drift
say "hello\nworld"
```

Lexer output conceptually looks like:

```text
TOKEN_SAY
TOKEN_STRING("hello\nworld")
TOKEN_EOF
```

The important detail is that the lexer converts the literal `\n` into a real newline inside the resulting string value, so later stages see the string as:

```text
hello
world
```

### Error handling in the lexer

The lexer reports:

- `Syntax Error: Unterminated string literal.` if the closing quote is missing
- `Syntax Error: Unknown token ...` for unsupported characters

This ensures malformed strings are rejected before parsing.

## 5. Parser layer

The parser consumes the token stream and builds a very small AST for the print statement.

Files involved:

- `include/drift/parser.h`
- `parser/parser.c`

### AST model

The parser defines a minimal AST node:

```c
typedef struct {
    char *value;
} PrintStatement;
```

This means the only AST node currently supported is a print statement containing a string value.

### What parser.c does

It expects the token flow to look like this:

```text
TOKEN_SAY TOKEN_STRING TOKEN_EOF
```

Then it builds a `PrintStatement` object containing the string value.

#### Parser behavior

- checks that the first token is `TOKEN_SAY`
- ensures the next token is `TOKEN_STRING`
- copies the string into the AST node
- ignores the trailing newline token if present
- accepts end-of-input only after the statement is complete

#### Syntax error examples

If input is:

```drift
say
```

parser emits:

```text
Syntax Error: Expected string after 'say'
```

If input is malformed or extra tokens are found, it reports a syntax error and stops execution.

## 6. AST and statement model

The AST is intentionally tiny. There is no huge tree with expressions, statements, scopes, or function calls.

Current AST is just one structure:

- `PrintStatement`

It contains:

- `char *value` — the text to print

This keeps the interpreter simple and ensures that parsing and execution remain easy to reason about.

## 7. Interpreter layer

The interpreter executes the AST and performs the actual output.

Files involved:

- `include/drift/interpreter.h`
- `interpreter/intptr.c`

### What interpreter.h does

It declares the runtime entry function:

```c
int interpreter_execute(PrintStatement *statement);
```

### What intptr.c does

The interpreter currently does this:

```c
printf("%s\n", statement->value);
```

So a `PrintStatement` with value `Hello` will print:

```text
Hello
```

That is the real execution stage of the language pipeline.

## 8. Main entry point

File involved:

- `main.c`

This is the top-level program that boots the interpreter.

### Responsibilities of main.c

- open the source file
- read its content into memory
- create a `Lexer`
- scan source into tokens
- create a `Parser`
- parse the AST
- execute the AST
- free memory

The interpreter can also support a REPL flow in the terminal, where input is typed directly:

```text
>>> say "Hello World"
Hello World
```

In this milestone, the language is designed around the pattern:

```text
>>> say "your message"
```

The program prints directly to stdout and exits when done.

## 9. How the entire pipeline works

Here is the exact flow for a simple command:

```drift
say "hello\nworld"
```

### Step 1: Source text

```text
say "hello\nworld"
```

### Step 2: Lexer tokenizes it

```text
TOKEN_SAY
TOKEN_STRING("hello\nworld")
TOKEN_EOF
```

The `\n` escape is converted into an actual newline inside the string.

### Step 3: Parser creates AST

```text
PrintStatement {
    value = "hello\nworld"
}
```

### Step 4: Interpreter executes AST

```c
printf("%s\n", "hello\nworld");
```

### Step 5: Runtime output

```text
hello
world
```

## 10. Why this is the right foundation

This architecture is intentionally minimal but correct.

It separates concerns cleanly:

- lexer handles text scanning
- parser handles grammar and structure
- AST holds the result of parsing
- interpreter executes the AST
- main controls file or REPL input

This is exactly how a real interpreter is structured, even though the language itself is tiny.

## 11. Files and responsibilities summary

- `main.c` — program entry point and source loading
- `include/drift/token.h` — token definitions
- `token/token.c` — token memory utilities
- `include/drift/lexer.h` — lexer structure and API
- `lexer/lexer.c` — scan source into tokens, process strings and escapes
- `include/drift/parser.h` — parser and AST declarations
- `parser/parser.c` — parse `say` statements into a `PrintStatement`
- `include/drift/interpreter.h` — interpreter API
- `interpreter/intptr.c` — runtime execution of print statements
- `Makefile` — compiles the project into `build/drift`

## 12. Current status

This milestone supports the minimal but complete pipeline for printing text:

```drift
say "Hello World"
```

and also supports escaped newlines inside quoted strings:

```drift
say "hello\nworld"
```

This is the foundation of the language and the correct starting point for future features such as arithmetic, variables, conditionals, loops, and functions.
