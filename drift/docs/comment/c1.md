# Comment Support in Drift

## Overview

Drift supports comments for documentation and code explanation, and it also supports executable code blocks inside documentation comments through the `@exc` and `.exc` markers.

The supported comment types are:

1. **Single-line comments** (`//`) - comments that continue to the end of the line
2. **Multi-line block comments** (`/* ... */`) - comments that can span multiple lines
3. **Executable documentation blocks** (`@exc` ... `.exc`) - code that is embedded in a comment block and executed by the interpreter

## Syntax

### Single-line Comments
```drift
var x = 10  // This is a single-line comment
say x       // Variables can have inline comments
```

### Multi-line Comments
```drift
/*
    This is a multi-line comment.
    It can span across multiple lines.
    None of this executes.
*/
var y = 20
```

### Executable Documentation Blocks
```drift
/*
    This is documentation.

    @exc
        say "Hello"
        var x = 10
        say x
    .exc

    This is still a comment.
*/
```

Important: in this updated format, `*` is not used to mark executable comment lines. The only markers are `@exc` and `.exc`.

### Inline Block Comments
```drift
var z = 30  /* This is an inline block comment */
say z       /* Comments don't affect execution */
```

## Implementation Details

### Files Modified

#### 1. **Makefile**
- Added `lexer/comments.c` to the source files list
- This ensures the comment handling code is compiled into the interpreter

```makefile
SRCS = main.c token/token.c lexer/lexer.c lexer/comments.c \
       parser/parser.c parser/array_parser.c parser/select_parser.c \
       interpreter/value.c interpreter/environment.c interpreter/intptr.c \
       interpreter/array_value.c interpreter/array.c
```

#### 2. **include/drift/lexer.h**
- Added two new fields to the `Lexer` struct:
  - `in_block_comment` - Tracks whether currently inside a block comment
  - `in_block_comment_code` - Tracks whether the current line contains executable code

```c
typedef struct {
    const char *source;
    size_t index;
    size_t length;
    int in_block_comment;           // NEW
    int in_block_comment_code;      // NEW
} Lexer;
```

#### 3. **include/drift/comments.h** (NEW FILE)
- Provides the public API for comment handling
- Three main functions:
  - `lexer_skip_comments()` - Skips over comments during lexing
  - `is_block_comment_open()` - Detects if a code snippet has unterminated block comments
  - `comments_reset_state()` - Resets comment state between operations

#### 4. **lexer/comments.c** (NEW FILE)
- Core implementation of comment handling logic
- `is_block_comment_open()` - Analyzes source code to detect open block comments
  - Handles string literals properly (ignores `/*` inside strings)
  - Tracks nested comment state
  - Returns true if a block comment is left open
  
- `lexer_skip_comments()` - Skips comments during tokenization
  - Handles both `//` and `/* */` comment styles
  - Preserves line tracking for error reporting
  - Skips comment content without creating tokens

#### 5. **lexer/lexer.c**
- Integrated comment skipping into the main lexing loop
- The lexer now calls `lexer_skip_comments()` when encountering `//` or `/*`

#### 6. **main.c**
- Updated REPL to detect unterminated block comments
- When user presses Enter with an open block comment, shows `...` prompt to continue
- Includes `#include "drift/comments.h"` for comment detection

```c
if (is_block_comment_open(input_buffer)) {
    printf("... ");
    fflush(stdout);
    continue;
}
```

#### 7. **parser/parser.c**
- No direct comment changes (handled at lexer level before parser)
- Parser receives a clean token stream with all comments stripped

## REPL Behavior

The REPL (Read-Eval-Print Loop) now handles multi-line block comments intelligently:

```
>>> var x = 10  /* start comment
... (waiting for comment closure)
... but this line is ignored
... */
>>> say x
10
>>>
```

When a block comment is opened but not closed, the REPL shows `...` as the prompt, indicating it's waiting for the comment to be terminated.

## Edge Cases Handled

1. **String literals** - `/* ... */` inside strings is not treated as a comment
2. **Escaped quotes** - Properly handles escaped quotes in strings
3. **Multiple comments** - Consecutive comments on the same line
4. **Nested comment markers** - `//` inside `/* */` is treated as part of the comment
5. **Incomplete input** - Detects unterminated block comments for REPL continuation

## Error Prevention

The comment implementation helps prevent parsing errors:
- Comments are completely stripped before parsing
- Parser never sees comment tokens
- This eliminates syntax errors from malformed comments being treated as code
